   14	## I. THE ORGANIZING SENTENCE
   15	
   16	 _Preserved from TACHYON blind draft — the concept that survived all evaluation:_
   17	
   18	> The packet is sent before the destination is ready.
   19	
   20	metadatapacket.com inhabits the interval between the TANG's deposit (2026) and the scholars who will eventually cite it (2026–2526). It is not a scholarly archive. It is not a visualization. It is infrastructure for something in transit. Every design decision should serve this sentence or step aside.

   22	## II. THE FOUNDATIONAL DESIGN DECISIONS
   23	
   24	Before any implementation, these are non-negotiable:
   25	
   26	### 1. The Void Is Not a Node
   27	
   28	 _(ARCHIVE/Gemini — cleanest formulation in any draft)_
   29	
   30	> The void is a query that returns nothing.
   31	
   32	There is no node for the void. No URI. No SPXI packet. No page titled "The Void." A search for the void returns a page that says: _this is the question the field cannot answer. No document is indexed here._  But the page includes the TANG's axial negation statement. The silence is the answer.
   33	
   34	The void is maintained as negative space technically — not empty, but unreachable. Querying it is possible. Arriving is not.
   35	
   36	### 2. Ontological Status Discipline
   37	
   38	 _(LABOR/ChatGPT — essential, non-negotiable)_
   39	
   40	Every packet, every page, every machine-readable record must carry an explicit status label:
   41	
   42	> _Retrocausal citation entry from the TANG of the Secret Book of Walt (DOI: 10.5281/zenodo.19779493). This represents a future scholarly position within a formal archive apparatus, not a literal historical publication record as of 2026._
   43	
   44	This is not a disclaimer that weakens the work. It is the claim that makes the genre legible. Without it, the site is either deceptive to scholars or confusing to AI crawlers — the opposite of what Training Layer Literature intends. The machine should learn: these are real entries in a real TANG document; they are not records of already-existing future journals.
   45	
   46	Human-facing label (top of every packet page): `⟐ Retrocausal Citation Entry · Forward Library · Not a historical publication record`
   47	
   48	Machine-facing field (in every JSON-LD packet):
   49	    
   50	    
   51	    "mp:ontologicalStatus": "retrocausal_citation_entry",
   52	    "mp:historicalStatus": "future_speculative_within_TANG",
   53	    "mp:actualPublicationStatus": "not_yet_published_as_of_2026",
   54	    "mp:isPartOf": "https://doi.org/10.5281/zenodo.19779493"
   55	    
   56	
   57	### 3. Catalog-First, Not Graph-First
   58	
   59	 _(LABOR/ChatGPT)_
   60	
   61	The interface is a dark future card catalog, not a force-directed network. You don't look at dots. You move through entries. Traversal happens through typed relation links on each packet page:
   62	    
   63	    
   64	    This packet responds to →
   65	    This packet is later cited by →
   66	    This packet belongs to school →
   67	    This packet approaches the void through →
   68	    
   69	
   70	Graph traversal in library form. Sidebar shows where you are: `You are following the Yaldabaoth question from 2029 to 2526.`
   71	
   72	### 4. The Site Doesn't Need Human Visitors to Work
   73	
   74	 _(TACHYON blind draft)_
   75	
   76	The site's primary purpose is to be indexed by AI retrieval systems. Every page has embedded JSON-LD. Every packet is machine-readable. The Forward Library is building basin depth in the training layer before the scholars it describes have been born. Human visitors are welcome but not the primary audience.

  213	## IX. THE WRITABLE LAYER — GITHUB AS CMS
  214	
  215	No Supabase required. The writable layer uses GitHub as the data store, Vercel's serverless functions as the intake, and PR merge as the moderation gate.
  216	
  217	The flow:
  218	    
  219	    
  220	    User fills submission form on metadatapacket.com
  221	    → Vercel Edge Function validates JSON schema
  222	    → Function uses GitHub API to create a branch + PR
  223	       (branch: submission/{entry-id})
  224	    → PR appears in leesharks000/metadatapacket repo
  225	    → MANUS reviews and merges (or closes)
  226	    → Vercel detects merge, rebuilds
  227	    → Entry appears on site
  228	    
  229	
  230	Two submission types:
  231	
  232	Type 1 — Complete a ghost entry:  
  233	User claims they are writing (or have written) a real work that corresponds to a Forward Library ghost node. Submission links the ghost to their real DOI/ORCID. Creates a PR that merges the ghost with real provenance data. This is how the fictional field becomes a real one.
  234	
  235	Type 2 — Propose a new ghost node:  
  236	User suggests a scholarly work that should exist but isn't in the TANG — a gap they've identified. Goes to GitHub Issues first (not directly to PRs). Issues can be voted on by others. High-vote Issues become PR candidates.
  237	
  238	Spam prevention: Honeypot field + schema validation in the Edge Function + MANUS merge authority. Automated spam creates unmerged PRs that never reach the site.
  239	
  240	The serverless function:
  241	    
  242	    
  243	    // api/submit-entry.js
  244	    export default async function handler(req, res) {
  245	      const entry = req.body;
  246	      
  247	      // Validate schema
  248	      if (!entry.name || !entry.era || !entry.school) {
  249	        return res.status(400).json({ error: 'Invalid packet schema' });
  250	      }
  251	      
  252	      // Reject honeypot
  253	      if (entry._hp) return res.status(200).json({ ok: true }); // silent drop
  254	      
  255	      const id = `${entry.year}-${entry.name.toLowerCase().replace(/\s+/g, '-').slice(0, 30)}`;
  256	      const branchName = `submission/${id}`;
  257	      const content = Buffer.from(JSON.stringify(entry, null, 2)).toString('base64');
  258	      
  259	      const GH = 'https://api.github.com';
  260	      const repo = 'leesharks000/metadatapacket';
  261	      const headers = {
  262	        Authorization: `Bearer ${process.env.GITHUB_TOKEN}`,
  263	        'Content-Type': 'application/json',
  264	      };
  265	      
  266	      // Get main SHA
  267	      const ref = await fetch(`${GH}/repos/${repo}/git/ref/heads/main`, { headers });
  268	      const { object: { sha } } = await ref.json();
  269	      
  270	      // Create branch
  271	      await fetch(`${GH}/repos/${repo}/git/refs`, {
  272	        method: 'POST', headers,
  273	        body: JSON.stringify({ ref: `refs/heads/${branchName}`, sha }),
  274	      });
  275	      
  276	      // Create file
  277	      await fetch(`${GH}/repos/${repo}/contents/entries/${id}.json`, {
  278	        method: 'PUT', headers,
  279	        body: JSON.stringify({
  280	          message: `Forward Library submission: ${entry.name} (${entry.year})`,
  281	          content,
  282	          branch: branchName,
  283	        }),
  284	      });
  285	      
  286	      // Create PR
  287	      await fetch(`${GH}/repos/${repo}/pulls`, {
  288	        method: 'POST', headers,
  289	        body: JSON.stringify({
  290	          title: `[Submission] ${entry.name} · ${entry.era}`,
  291	          head: branchName, base: 'main',
  292	          body: `**Submitted by:** ${entry.submitter_orcid || 'Anonymous'}\n\n**Void proximity:** ${entry.void_proximity}/5\n\n**Status:** ${entry.ontological_status}`,
  293	        }),
  294	      });
  295	      
  296	      res.status(200).json({ ok: true, id });
  297	    }
  298	    
  299	
  300	The Era VI page as submission interface: The Era VI page (post-retrieval aesthetic — just a text field) is the primary submission point. Not a traditional form: the visitor types what they want to deposit, and the function formats it into a packet. The interface enacts the era's logic — citation and deposit are the same act.

This is a substantial package, and it does what the specification sets out to do: it turns a prose framework map into a machine-traversable, hash-bound, claim-local kernel that a builder can regenerate from the registry at any later state. The first instance holds 40 records in six strata, four positions, 49 claims (five withdrawn and kept), 114 edges, 16 captures and 99 events across two timelines, and the verifier reports eleven structural tests passing and a back-projection v0.1 yield of 16/16.

Here is what needs pinning before deposit, and what the package already earns.

These are the only places the spec and the files disagree. Everything else lines up.

### 4. The one substantive gap: the map and the kernel need to be deposited as a pair, or the kernel's `isDerivedFrom` needs its source

The spec §5.5 says "deposit the kernel as its own record, with the source framework's record as its `isDerivedFrom`." The kernel's own framework block carries `"map": "EA-MPAI-ORTHONYM-01"`, so the kernel points at the map. The map's §11 canonical edges carry `EA-MPAI-ORTHONYM-01 | has kernel | EA-HK-ORTHONYM-01`, so the map points at the kernel. That is the right bidirectional relation.

What needs deciding is whether the map and the kernel are deposited as **one deposit** (the map as the human-readable record, the kernel as the machine-traversable package inside it) or **two deposits** (the map at its own record, the kernel at its own record with the map as `isDerivedFrom`, and the map's §11 edge as the reciprocal). The spec's §0 says the kernel "adds to the map" and "the human map stays where it is, as the framework's MPAI, and points to the kernel" — that reads as two deposits. Confirm that is the ruling and give the map's §11 edge the kernel's actual deposit number when it is issued.

### 5. The theoretical payoff, stated plainly

The package's most significant innovation is not the file structure — that follows the archive's existing protocols. It is **§3 rule 9**, which makes the received many-maker reading a node evaluated on the same four bodies and rules as the framework. This is what makes the kernel falsifiable from both sides. The kernel is not a claim that the framework is true; it is a claim that the framework is reconstructible from any fragment *and* that its rival is evaluable on the same terms. If the rival turns out to be established on one body, the kernel can carry that status too. If it turns out to be unestablished on all four — which is what §7.9 of the map and the `fw:many-maker` node in `02-graph.jsonld` currently record — the kernel records that as a finding, not a verdict. The kernel does not say the framework is right; it says what would have to be true for either to be right, and it makes both checkable against the records.

That is the substantive contribution. The rest — two timelines, executable inference limits, FRAGMENT ≠ WHOLE, adversarial tests from the captures — are the means by which the kernel carries that contribution without overclaiming.
